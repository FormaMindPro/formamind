# Конфигурация проекта

Заполняется для конкретного проекта и живёт всю его жизнь. Правила находятся в `AGENTS.md` и не меняются.

Здесь — с чем работаем и на каком уровне. Что строим и в каком порядке — в `ROADMAP.md`. Сегмент — в `goals/goal-NN/GOAL.md`.

**Язык проекта** <!-- k:language --> *(человек, до старта; задаёт язык карточек задач, целей и документации — `AGENTS.md` §6)*: Русский. Документация самой схемы (`manual/`) не переводится на язык проекта: существует на английском — оригинал, `manual/en/` — и на русском — точная копия, `manual/ru/`.

| Поле | Значение |
|---|---|
| Имя <!-- k:name --> | — |
| Источник <!-- k:source --> | — |
| Статус <!-- k:status --> | `none` |
| Маршрут | `project/config/ROUTE.md` — эталон для пятой позиции интервью |

**Три возможных статуса, закрытый список:** `verified ready` — маршрут пройден до результата, пятая позиция сводится к проверке; `forming with the human` — маршрут частично написан, сверяемся с написанным и достраиваем недостающее; `none` — неизвестная территория, маршрута нет, все пять позиций прорабатываются на одинаковую глубину. Сценарий интервью один и тот же в любом случае и поставляется с ядром: шаблон добавляет только эталон к пятой позиции.

**Эпики проекта** <!-- k:epics --> *(человек, до старта; роль и процедура каждого фиксированы, `intent.md`, «Эпик», код в скобках проверяет их перекрёстно; имя в этой колонке — единственное, что настраивается для конкретного проекта здесь)*:

| Код | Эпик в этом проекте | Назначение |
|---|---|---|
| `analytics` | 1. Аналитика проекта | замечание по производственному расходу самого проекта — токены, кэш, попытки, цена круга: `Core` читает тренд, `Intent` держит «дёшево» |
| `structure` | 2. Структура проекта | документация самого продукта, для человека: пользовательская, административная, техническая — как работать с тем, что мы производим. Круг цели закрыт, и данное им обещание должно быть показано сдержанным: `Intent` читает зоны «Результат» закрытых карточек, смотрит на живой результат и пишет раздел `project/docs/` для человека |
| `protocol` | 3. Протокол проекта | узел дошёл до строки маршрута «человек»; разведка незнакомого стека узлом `Kit` перед нарезкой; инфраструктура движка, скрипты, скиллы, адаптеры. Обязательные скиллы: `skill-authoring` (создание скиллов), `vdisk-setup` (тесты/сборки), `scaffold-sync` (шаблоны), `engine-switch` (адаптеры). Требования: код и скиллы только на английском языке |
| `resources` | 4. Ресурсы проекта | интервью `grilling` при открытии новой цели |
| `balance` | 5. Баланс формы | предложения `Core` при закрытии круга: `Core` пишет замечание, `Intent` раскладывает его по доменам |
| `discussion` | 6. Разбор дел | исправление или задача, появившаяся по ходу и не требующая немедленного ухода в производство: `Intent` либо быстро решает её сам и закрывает карточку, либо отдаёт `Spec` на нарезку. Здесь же — карточка без нарезки и дефект за пределами текущей цели |
| `channels` | 7. Каналы производства | сам продукт: главная цель `goal-channels` и подцели `goal-NN` на одной дорожке, цель выбирается меткой |
| `competencies` | 8. Сегменты компетенций | прополка хранилища `project/experience/`: разошедшиеся ключи, противоречащие записи |
| `results` | 9. Достижение целей | вне производственного цикла. Собственный процесс тестирования человека, сформированный им для себя: как проверяется результат, правки к работе и тестированию, дополнения к тому, что предполагалось получить в конечном итоге — образ результата и итоговая приёмка/тестирование могут различаться. Является дополнением к уже сформированной цели, не переписыванием: `GOAL.md` не меняется (запрет 8), дополнение фиксируется рядом, и только человек превращает его в новую цель или переоткрытие. Собственная процедура тестирования, привязанная к отдельным процессам |

**Эпик — это разновидность цели, цель — это метка.** Девять видов идут параллельно; у каждого есть главная цель `goal-<code>` и, при необходимости, подцели `goal-NN` (сквозная нумерация). Карточка несёт ровно одну метку цели в `labels` — это подлинная связь; эпик — лишь дорожка её типа (`AGENTS.md` §6, `intent-goal-opening.md`, «Эпик»). Кто формирует цель каждого типа — там же, «Как формируются цели».

**Список видов — не обязанность по каждой цели.** Проект объявляет, какие виды здесь есть; какие из них должна конкретная цель — называет её образ результата. Цель, чей образ молчит о документации, ничего не должна — добавление вида задним числом расширило бы обещание после того, как оно было дано, а это человек, переоткрывающий образ, а не решение узла.

**Где живёт.** `project/docs/goal-NN-<name>/`, по одному файлу на вид. Раздел цели накапливается по кругам, а не перестраивается заново: каждый закрытый круг дописывает своё.

**Квалификация узлов** — не отдельное поле, не заполняется заранее. У каждого узла свой источник уровня, считываемый на месте, когда узел реально смотрит на задачу:

| Узел | Источник уровня |
|---|---|
| `Intent` | бриф/интервью — узнаёт по ходу разговора, кто в этой области судит о результате |
| `Spec` | `ROADMAP.md`/`GOAL.md` конкретной цели — как принято нарезать работу здесь, на месте, при нарезке |
| `Kit` | собственный поиск по арсеналу (скилл `skill-authoring`, «Источники готового») — проверяет сам, с чем работать |
| `Run` | карточка + комплект, выданный `Kit` — уровень уже в задаче, называть его отдельно не нужно |
| `Core` | не меняется по проектам — фиксированная роль протокола (`PROTOCOL.md`, «Квалификация») |

Уровень передаётся по цепочке документов, которые и так находятся перед узлом (бриф → `ROADMAP.md`/`GOAL.md` → карточка → комплект), а не хранится отдельной строкой, которую человек должен выдумать до старта.

## Что попадает в кэш цикла

Из этого файла кэш берёт: оснастку узлов, пороги, доступы и данные, справочники проекта — по ссылке и версии. Образ результата прибывает отдельно — из `GOAL.md` текущей цели.

Не входит: «Чего не хватало» (`JOURNAL.md` + карточки эпика «3. Протокол проекта») — это материал для `Spec` при нарезке, а не фон для каждого вызова.
